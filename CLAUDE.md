# Lowballer.org

AI-powered marketplace deal appraiser. Users screenshot a Facebook Marketplace listing, Copart lot, or any resale listing; the app extracts details with Claude vision, researches live market comps and repair costs via Claude + web search, and outputs a verdict with an exact lowball offer or max auction bid.

## Business model
- **Pay per result, no free tier.** Every non-Pro appraisal runs in full, but the server keeps the result and sends only a teaser (verdict / score / counts — see `buildTeaser` in `lib/lockedResults.js`). The page shows the teaser for ~3s (`PREVIEW_MS`), then blurs placeholder content behind an unlock panel. One result unlocks for $5 (`UNLOCK_PRICE_CENTS`, default 500) via a one-time Stripe Checkout — no account needed. The paid details never reach the browser before payment.
- Pro: $30/month unlimited (full results, never locked), via Stripe Checkout subscription

## Stack
- Next.js 14 (App Router, JavaScript, no TypeScript)
- React 18, all styling inline + a single <style> block in `app/page.jsx` (no Tailwind, no CSS modules)
- Look: dark, app-style. Tokens live in `C` at the top of `app/page.jsx` — near-black surfaces, **lime (`C.lime`) is reserved for "your number"** (the offer / max bid / primary CTA), violet for links and secondary accents. Headings use Space Grotesk (`display`), body Inter, numbers IBM Plex Mono — fonts load in `app/layout.jsx`. Signature pieces: scan-first home (Link scan / Photo scan cards, segmented mode switch), `Gauge` (half-dial deal score with a needle) and `PriceRange` (market band with asking + offer markers). It's inspired by app-style competitors but deliberately not a copy — keep our own palette, gauge and wording.
- Postgres + Prisma (accounts, sessions, entitlement, appraisal history) — hosted on Railway in this project
- Stripe SDK for subscriptions
- Anthropic Messages API (model `claude-sonnet-4-6`) with the `web_search_20250305` tool
- Resend for magic-link emails (optional in dev — see Auth section)

## Architecture
- `app/page.jsx` — the entire UI (client component). Three modes: car, item, salvage. Each appraisal is ONE research POST to `/api/appraise` (salvage asks for value + repairs in a single prompt so the whole flip check is one lockable result); extraction is a separate no-search call. `LockedPreview` renders a locked result; `applyResult` / `openResult` rebuild the view from a result id (after the Stripe redirect `/?unlock=<id>&unlock_session=…`, after going Pro from a locked result, or on a cancelled checkout). Sign-in modal, nav auth state, and a 401-from-appraise handler live here too.
- `app/api/appraise/route.js` — the ONLY place the Anthropic key is used. Proxies to api.anthropic.com, parses the JSON out of Claude's text response. Rate-limited via `lib/rateLimit.js`: a blanket per-IP cap (30/15min) on every call, a per-user cap (20/hr) on research calls (what bounds Pro spend), and for non-Pro research calls 8/day per IP plus a shared daily cap (`LOCKED_DAILY_CAP`, default 300) — locked runs cost a full analysis before anyone pays. **The server decides what's paid, not the client**: any research call (web search, or `analysis: "vehicle"`) by a non-Pro user is stored via `saveResult` (locked) and answered with `{ locked, resultId, mode, teaser, price }`; Pro results are stored too (`paid: true`) and come back with a `resultId`, so every result can be reopened, shared, compared and negotiated; there is no client `count` flag any more, so a crafted request can't pull research results out for free. Plain extraction (no search) stays open and unlocked. Signed-in research runs also write an `Appraisal` history row.
- `lib/anthropic.js` — shared Anthropic Messages wrapper (`callAnthropic`, `webSearchTool`, `upstreamFailure`, `extractJson`, `searchedUrls`/`searchedSources`). `upstreamFailure` maps upstream errors to distinct responses (bad key → 502 `ai_auth`, 429 → `ai_busy`, 503/529 → `ai_overloaded`, exhausted credits → `ai_credits`); details are only logged server-side.
- `lib/vehicleAnalysis.js` — the vehicle deal analysis behind `POST /api/appraise` with `{ analysis: "vehicle", listing, images }` (car mode). The server builds the prompt (listing text is wrapped in tags and treated as untrusted), makes ONE web-search call, validates the JSON against a hand-written schema (no dependency) and retries once without search on a validation failure, else returns `analysis_invalid` (and refunds the free use). Output: `verdict` (steal|fair|overpriced|money_pit) + `deal_score` + `reason`, `market_value` (low/mid/high + comps), `red_flags`, `repair_estimate`, `flip_potential`, `inspection_checklist`, `meta`. Anti-hallucination rules live in code, not just the prompt: a flag quoting the listing must quote text actually in it, photo flags need attached images, comp URLs must appear in the real search results (else the comp is dropped and `basis` falls back to `estimate`), repair totals and flip math (`FLIP_PREP_COST`, `FLIP_MIN_PROFIT`, `FLIP_MIN_PCT`; no-go if any high flag) are computed in JS, and a deterministic backstop flags prices far below market. A vehicle request is always metered as exactly one free use however many photos (up to `MAX_IMAGES` = 6, compressed client-side by `compressImage` in `app/page.jsx`); the client can't turn metering or search off. The route's `maxDuration` is 180s.
- `lib/listingFetch.js` + `app/api/listing/route.js` — Marketplace link scans. `POST /api/listing { url }` finds a Facebook link anywhere in the pasted text (the FB app's Share button copies "Check out this listing… <link>") and accepts `facebook.com/marketplace/item/<id>`, share links (`facebook.com/share/[x/]<code>`, `fb.me/<code>` — opaque, resolved by the vendor, which returns the real item id; cached as `lb_listing:fbshare:<code>` → item id; unresolvable ones return `share_unresolved`), and `l.facebook.com/l.php?u=` wrappers (unwrapped locally, no fetch). Everything is canonicalized, so the vendor never sees arbitrary input; loads the listing through ScrapeCreators (`SCRAPECREATORS_API_KEY`; one synchronous GET, 1 credit), caches it in Redis 6h (`lb_listing:fb:<id>`; dead links 10 min), downloads up to 6 photos from fbcdn as base64 (not cached — too big for Redis), and returns `{ listing, text, images }`. The client then runs the normal extraction step and the user runs the normal appraisal, so metering is unchanged — the link scan itself isn't metered but is rate-limited (20/15min per IP, 30/hr per user). Gated by `LINK_SCAN_MODE`: `off`, `testers` (default; only `LINK_SCAN_TESTERS` emails), `pro` (subscribers + testers; everyone else sees it as a Pro upsell), or `all` (everyone, including signed-out — the growth setting). Non-Pro scans are capped at 10/day per IP, and uncached ones draw on a shared daily credit budget (`LINK_SCAN_FREE_DAILY`, default 200, Redis key `lb_listing_budget:<date>`) — over budget returns `busy` and the screenshot fallback. `/api/me` returns `linkScan: "on" | "pro_only" | "off"`. Any failure returns `fallback: "screenshots"` and the UI points to the upload. To swap vendors, replace `fetchFromVendor` + `normalizeFacebookItem`.
- `lib/negotiate.js` + `app/api/negotiate/route.js` — negotiation coach. Paid (unlocked/Pro) results only (402 otherwise, so it can't be used to back out a locked result's numbers). One no-search Claude call per turn that only READS the seller's message (their price, whether it's final) and drafts replies with a `{PRICE}` placeholder; `decide()` picks accept / counter / hold / walk and the price in plain JS from the user's open/target/walk-away numbers — counters are rounded but never above walk-away, accepts use the seller's exact price. The client sends its own offer numbers (deterministic deal math lives in `app/page.jsx`); they're sanity-checked by `cleanNumbers`. Threads persist per result in localStorage (`lb_coach:<resultId>`).
- `lib/shares.js` + `app/api/share/route.js` + `app/d/[id]/page.jsx` + `app/d/[id]/opengraph-image.jsx` — shareable deal cards. A share is a teaser-level SNAPSHOT under its own id (`lb_share:<id>`, one per result via `lb_share_for:<resultId>`): title, verdict, score, asking, red-flag counts, and "% under asking" only for paid results. Client-sent `offerTarget` / `verdictLabel` only count for paid results, and verdict labels are whitelisted. The OG image uses `next/og` (built into Next — no dependency); satori needs `display: flex` on any element with more than one child. `metadataBase` in `app/layout.jsx` makes the image URLs absolute.
- In `app/page.jsx`: seller-message styles (`sellerMessages` — friendly / firm / cash today / "I know cars", text-length, follow-up; plain templates, no AI), `Coach`, `ShareButton`, and `DealsPanel` ("My deals" — every result that lands is saved in localStorage `lb_deals`, max 20, reopen via `openResult`, tick 2–3 to compare side by side with a "best buy" pick).
- `lib/auth.js` — `getCurrentUser()` (reads the signed `lb_sess` cookie, loads the Session + User, null if missing/expired), session cookie helpers. This is what replaced the old `readAccount(cookies())` cookie-only check.
- `app/api/auth/login/route.js` — `{ email }` → upserts a User, mints a single-use 15-minute LoginToken (only the hash is stored), emails the link via `lib/mail.js`. Always the same response whether or not the email has an account. Rate-limited via `lib/rateLimit.js`.
- `app/api/auth/callback/route.js` — verifies the token (atomic claim so a link used twice only ever succeeds once), creates a Session, sets the signed `lb_sess` cookie (30 days), redirects to `/?auth=ok` (or `/?auth=invalid`).
- `app/api/auth/logout/route.js` — deletes the Session row server-side (not just the cookie) and clears it.
- `app/api/me/route.js` — returns `{ email, pro, configured, linkScan, unlockPrice }`.
- `lib/mail.js` — `sendMagicLink()` via the Resend REST API; logs the link to the console instead when `RESEND_API_KEY` isn't set, so local dev needs no email provider.
- `lib/rateLimit.js` — sliding-window limiter backed by Upstash Redis (`UPSTASH_REDIS_REST_URL`/`_TOKEN`), shared across every serverless instance. Started as an in-memory version, which provided close to no real protection on Vercel (32 rapid requests against a 30-request limit all succeeded in live testing). One `Ratelimit` instance per distinct `(max, windowMs)` pair, created lazily and cached. Also exports `dailyBudgetOk(name, cap)` — a per-UTC-day Redis counter for spend that must be bounded across all visitors, not just per IP.
- `app/api/checkout/route.js` — creates a Stripe Checkout Session. Requires a signed-in user (401 if not) and always uses their real email for `customer_email` — never trust one from the request body.
- `app/api/checkout/verify/route.js` — fast-path UI signal only for the Pro subscription (checks the session with Stripe, returns `{pro}` — only for `mode: "subscription"` sessions, so a $5 unlock can't read as Pro). Grants nothing itself; sets no cookie. The webhook writing to the `User` row is the actual source of truth.
- `lib/lockedResults.js` — results in Redis (`lb_result:<id>`, unguessable 24-char id): `saveResult` (locked, or already paid for Pro), `getResult`, `markPaid` (idempotent), `buildTeaser`. **A paid result's id is effectively a key to the full result** (`/api/result/:id` returns it to anyone) — never put it in a public URL; share cards use their own ids. Unpaid results expire after 7 days, paid ones are kept a year. Stores the form `inputs` too so the page can rebuild after the Stripe redirect.
- `app/api/unlock/route.js` — `{ resultId }` → one-time $5 Stripe Checkout (`mode: "payment"`, inline `price_data`, `metadata.kind = "unlock"`). No sign-in needed; prefills the email if signed in. Success URL uses `unlock`/`unlock_session` params — deliberately not `session_id`, which is the Pro flow's.
- `app/api/result/[id]/route.js` — returns the full result once paid (or to a Pro user), otherwise the teaser. `?unlock_session=` is the fast path after the redirect: the session is verified with Stripe and must be a paid unlock for THIS result id.
- `app/api/stripe/webhook/route.js` — Stripe is the source of truth for subscription status and unlock payments. Verifies the signature against the **raw** request body (`req.text()`, never `req.json()`). `checkout.session.completed` with `metadata.kind === "unlock"` only marks that result paid (`markPaid`) and never reaches `setSubscription`; any other non-subscription checkout is ignored — only `mode: "subscription"` sessions grant Pro. Then syncs `checkout.session.completed` / `customer.subscription.updated` / `customer.subscription.deleted` / `invoice.payment_failed` into `lib/subscriptions.js`. Always acknowledges with 200 except on bad signature (400) — an unhandled event type or an internal processing error still returns 200, or Stripe retries the event forever. `invoice.payment_failed` marks `past_due` but does NOT revoke access (Stripe retries failed payments; revoking on the first failure punishes an expired card, not a real cancellation).
- `lib/subscriptions.js` — `setSubscription` / `getSubscriptionByEmail` / `isEntitled`, now backed by Prisma (the `User` row's `stripeCustomerId`/`subscriptionStatus`/etc.) rather than the Phase 1 JSON file. Matches by email; creates a `User` if none exists yet, since someone can subscribe before ever signing in.
- `lib/db.js` — Prisma client singleton (reused across hot reloads in dev so edits don't exhaust the connection limit).
- `lib/sign.js` — HMAC sign/verify (used for both the session cookie and login/session tokens).
- `prisma/schema.prisma` — `User` (identity + entitlement; `freeUsesConsumed` is left over from the old free tier and no longer read), `Session`, `LoginToken` (hash stored, never the raw token), `Appraisal` (usage history, one row per signed-in research run).

## Auth (magic link, no passwords)
- Sign-in is email-only: request a link, click it, done. No passwords, no password-reset flow.
- In dev, if `RESEND_API_KEY` isn't set, the link is printed to the server console instead of emailed — sign-in still works end to end, just copy the URL from the terminal.
- Sessions last 30 days (`lb_sess`, HMAC-signed, httpOnly). Signing out deletes the `Session` row server-side, not just the cookie.
- Do not add NextAuth or another auth framework here — the session needs are small and `lib/sign.js` + this setup already cover them; a framework would cost more than it saves.

## Conventions
- Keep the Anthropic API key server-side only. Never move AI calls to the client.
- Claude prompts always demand compact JSON with an exact schema; the server extracts the first `{...}` block. If you change a schema, change both the prompt and the UI fields that read it.
- Deal math (offer percentages, Copart fee tiers, rebuilt-title discounts, hidden-damage buffer) lives in `app/page.jsx` — it's business logic, keep it deterministic in JS rather than asking the AI for it.
- Amounts render through `fmt()`; keep money as numbers until display.
- Never trust the client for entitlement or for which email a request belongs to — always resolve it server-side from the session (`getCurrentUser()`).

## Commands
- `npm run dev` — local dev at http://localhost:3000
- `npm run build` — production build (must pass before deploying)
- Copy `.env.example` to `.env.local` and fill in keys before running.
- Prisma CLI reads `.env`, not `.env.local` (Next.js's convention) — keep a `.env` with just `DATABASE_URL` mirrored in it for `npx prisma migrate dev` / `npx prisma studio` to work without manually prefixing the env var. `.env` is gitignored, same as `.env.local`.
- `npx prisma migrate dev --name <name>` — create and apply a migration after changing `prisma/schema.prisma`.
- `stripe listen --forward-to localhost:3000/api/stripe/webhook` — forwards Stripe events to the local webhook in dev; it prints the `whsec_...` signing secret to put in `STRIPE_WEBHOOK_SECRET`. `stripe trigger checkout.session.completed` / `stripe trigger customer.subscription.deleted` simulate events.
- In production, add the webhook endpoint in the Stripe dashboard (Developers → Webhooks) pointed at `https://<your-domain>/api/stripe/webhook`, subscribed to `checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.payment_failed`, and put that endpoint's signing secret in `STRIPE_WEBHOOK_SECRET` on the host.

## Known limitations / roadmap
- Marketplace link scans depend on a third-party vendor (ScrapeCreators), so they can break when Facebook changes and each uncached scan costs a credit. Screenshots are always the fallback and must keep working on every plan.
- The generic (non-`analysis`) path of `/api/appraise` still accepts arbitrary `content` from the client. Research calls are locked for non-Pro, but plain extraction calls (no search) are open, so anyone can get unmetered no-search Claude calls bounded only by the 30/15min per-IP rate limit. Moving item/salvage prompts server-side (like the vehicle analysis) would close it.
- Unpaid locked runs are bounded per IP (8/day) and globally (`LOCKED_DAILY_CAP`/day). Someone rotating IPs can still burn analyses up to the global cap without paying — that cap is the spend ceiling.
- Upstash's `slidingWindow` algorithm is an approximation (weighted across two fixed windows), not an exact sliding log — live testing showed 31 requests through a 30-request limit before blocking. Fine for a spend cap; don't rely on it for exact-count guarantees.
- Facebook Marketplace has no API. Pasted Marketplace links are loaded ONLY through the listing-retrieval vendor in `lib/listingFetch.js` — never write our own Facebook fetching/scraping code, never use anyone's Facebook session or cookies. Screenshots stay the universal path.
- Prisma installs the latest major by default (7.x at time of writing), which requires a `prisma.config.ts` for `DATABASE_URL` instead of the classic schema-file `url`. This project pins `prisma`/`@prisma/client` to 6.19.3 deliberately, to stay on the plain-schema pattern and avoid needing TypeScript config in a JS-only project. Don't casually `npm update` past the 6.x line without checking what that migration actually requires.

## Browser extension (`extension/`)
Chrome MV3 extension that adds a "Lowball this" button to listing pages (Facebook Marketplace, Craigslist, eBay, OfferUp, Copart, IAAI).

- Reads only the page the user is actively viewing, on click. No cookie access, no background crawling, no requests to third-party sites on the user's behalf. Do NOT add scraping or session-cookie features — that is a ToS and account-risk line we don't cross.
- Handoff is via URL fragment: `https://lowballer.org/#lb=<base64url json>`. Fragments never reach the server, so no CORS, no cross-site cookies, and metering/Stripe stay first-party in the existing site session.
- `app/page.jsx` decodes the fragment on mount (payload v1), sets mode, prefills fields, clears the hash, shows an import banner.
- Extraction in `extension/content.js` is LAYERED, not selector-based: L1 JSON-LD → L2 OpenGraph meta → L3 embedded JSON field names → L4 semantic DOM (h1/itemprop/data-testid) → L5 visible text. Each field records its source layer and the payload carries a `confidence` score.
- Do NOT add generated CSS class selectors — that's what made v1 fragile. To support a new field or site, add keys to `EMBEDDED_KEYS` and/or a `content_scripts.matches` entry; extraction itself is generic.
- Visible text always ships in `rawText` as the safety net, so a low-confidence read still gives Claude enough to parse. Keep that guarantee.
- Payload is v2; `app/page.jsx` accepts v1 and v2. Bump the version and keep backward compatibility if the shape changes.
